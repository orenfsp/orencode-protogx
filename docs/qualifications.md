# AC-09: разряды и судейские категории

Статус: **partial** — исправления проходят проверку; юридическая проверка источников и пользовательский интерфейс отзыва согласия остаются открытыми.

## Поток

```text
Опубликованный протокол → проверенный результат
  → (подсказка: результат может подойти по настроенному правилу — предварительная, не присвоение)
  → спортсмен без подтверждённого тренера, либо тренер с подтверждённой связью по дисциплине, подаёт заявку
    (результат-основание, запрашиваемый разряд, присвоение/подтверждение)
  → федерация: присвоить (приказ, дата, срок действия) или отклонить (причина)
  → неизменяемая запись истории + AuditEvent → контроль сроков
```

Судейские категории — отдельный аналогичный поток: судья подаёт заявку за себя (одна на рассмотрении),
федерация присваивает или отклоняет. Категории и разряды не смешиваются. Подача в Госуслугах — вне платформы.

## Модели (`apps/qualifications`, миграция `0001_initial`)

| Модель | Назначение / ограничения |
| --- | --- |
| `QualificationRule` | Настраиваемое правило подсказки: дисциплина, разряд, уровень соревнования (текст, сравнение без регистра), `max_place`, `rule_version`, `source_verified` (по умолчанию false). Unique `(discipline, rank, competition_level, rule_version)` |
| `RankApplication` | Спортсмен, подавший, тип (assign/confirm), разряд, дисциплина, соревнование и **результат**, статус, решение. Unique `(result, requested_rank)` пока `pending` |
| `SportRankHistory` | Запись о присвоении: разряд, приказ, дата, срок. One-to-one с заявкой; CHECK `valid_until > assigned_on`. Не перезаписывается |
| `JudgeCategoryApplication` | Судья, тип, категория, статус, решение. Не более одной `pending` на судью |
| `JudgeCategoryHistory` | Аналог `SportRankHistory` для категорий |

Справочники разрядов и категорий — `TextChoices` в `models.py`; это демонстрационный перечень без заявления о соответствии ЕВСК.
Правила подсказки не засеваются миграцией: `python manage.py seed_qualifications` (только `DJANGO_DEBUG=1`) создаёт условные правила,
помеченные «не сверено с ЕВСК».

## API (`/api/v1/`, сессия + CSRF, активная роль проверяется на сервере)

| Метод и путь | Роли | Поведение |
| --- | --- | --- |
| `GET qualification-options/` | любая назначенная | перечни разрядов, категорий, типов; текст дисклеймера |
| `GET qualification-rules/` | federation | правила подсказки |
| `GET rank-results/?hinted=1` | federation (все), athlete (свои), coach (подопечные) | проверенные classified-результаты опубликованных протоколов, подсказка, текущий разряд, ожидающие разряды |
| `GET/POST rank-applications/` | GET: federation/athlete/coach; POST: athlete/coach | список по объекту; подача по правилам ниже |
| `POST rank-applications/{id}/decision/` | federation | `{status, reason?, order_number, assigned_on, valid_until}` |
| `GET rank-history/?athlete=` | federation/athlete/coach | история; тренер — только подтверждённые связи по дисциплине |
| `GET/POST judge-category-applications/` | GET: federation/judge; POST: judge | |
| `POST judge-category-applications/{id}/decision/` | federation | как для разрядов |
| `GET judge-category-history/` | federation/judge (свои) | |
| `GET qualification-deadlines/?days=60` | все четыре | разряды/категории, истекающие в окне или уже истёкшие, в пределах прав роли |

Правила подачи: результат существует, `classified`, проверен федерацией (`validated_by`), протокол соревнования опубликован;
athlete — только за себя и только если по дисциплине нет подтверждённого тренера; coach — подтверждённая связь по дисциплине результата;
дубликат `pending` запрещён; «присвоение» — строго выше действующего разряда; «подтверждение» — только ранее присвоенного.
Решение: отказ требует причину; присвоение — приказ, дату (не в будущем) и срок действия позже даты; повторное решение запрещено.
Все переходы пишут `AuditEvent` (`rank_application.*`, `judge_category_application.*`) в той же транзакции.
«Текущая» запись человека — высший из действующих уровней (иначе высший из истёкших); заменённые записи ложных предупреждений не дают.

## Известные ограничения

- Уведомления об изменении статуса и об истечении срока (AC-10) не реализованы; сроки видны в кабинете и по API.
- Вложение документов к заявке не реализовано (только текстовый комментарий).
- При подаче разряда проверяются последняя запись персонального согласия (она не должна быть отозвана) и подтверждённый опекун несовершеннолетнего. Дата отзыва хранится в `revoked_at`; пользовательский интерфейс и процесс отзыва не реализованы. Срок действия согласия модель не задаёт.
- Совпадение уровня соревнования с правилом — по тексту `Competition.level` без регистра; федерация задаёт правила под принятые названия.
- Правила подсказки демонстрационные и не подтверждены первоисточником; их нельзя представлять как нормы ЕВСК.
- Модель `JudgeProfile` не создавалась: судья идентифицируется ролью `judge`.
- Новые заявки сохраняют ID последней публикации и копию строки участника из её снимка. Старые записи без подтверждённого источника остаются с пустой привязкой; прошлый источник не угадывается. `rank-results/` возвращает `items`, `page`, `pages`, `count`, `has_next` и страницы по 50 результатов; `count` считает кандидатов до проверки строки снимка.
- Заявки и история доступны в Django admin только для чтения. Коррекция ранее созданной исторической записи пока не реализована; повторное присвоение создаёт новую запись через существующий аудируемый процесс.

## Как проверить

```text
docker compose exec -T api python manage.py makemigrations --check --dry-run   # ожидается No changes detected
docker compose exec -T api python manage.py migrate
docker compose exec -T api python manage.py test tests.test_qualifications
docker compose exec -T api python manage.py test
docker compose exec -T api ruff check .
docker compose exec -T api python manage.py seed_qualifications               # DJANGO_DEBUG=1
cd frontend && npm.cmd run typecheck && npm.cmd run lint && npm.cmd run build
python scripts/check_design_contract.py
```
Ручной сценарий: federation публикует соревнование с уровнем «Региональное» → результат внесён и проверен → протокол опубликован →
демо-спортсмен открывает `/qualifications`, выбирает результат, отправляет заявку → federation присваивает с приказом и сроком →
запись появляется в «Разряды» спортсмена и в реестре федерации.
