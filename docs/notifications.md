# Уведомления и контроль сроков

Модуль `backend/apps/notifications` добавлен по заданию mandatory part 1. Внешний канал — email: кейс с.5 разрешает один канал на выбор, а проектный AC-10 дополнительно требует email.

## Контракт

- `GET /api/v1/notifications/`: последние 100 сохранённых событий только текущего пользователя и назначенной активной роли. Порядок — новые сначала. Поля: id, kind, title, body, created_at, read_at, status, attempts, sent_at, error_code.
- `POST /api/v1/notifications/{id}/read/`: идемпотентная отметка прочтения; чужой пользователь или другая активная роль получает 404; отозванная роль — 403. Требует session и CSRF.
- `GET/POST /api/v1/report-deadlines/`: сроки отчётов, доступ только активной федерации. Создание аудируется. Кабинет федерации содержит форму.
- Кабинет показывает сохранённые события и состояние email; чтение не меняет состояние доставки. Временные Toast сообщения остаются отдельным UI механизмом.

`Notification` одновременно является inbox и транзакционным outbox; уникальны `(event_key, recipient, role)`. События создаются синхронно существующим доменным audit service в транзакции операции. Нет отдельного брокера и второго event bus. Внешний SMTP вызывается только worker после коммита доменной операции.

Публикация соревнования, подача/решение по заявке, публикация каждой версии протокола, подача/решение по разряду и категории создают уведомления. Возобновление регистрации имеет отдельный ключ по audit event. Результаты и причины решения не включаются в email. Каждое письмо имеет ровно одного получателя. Тренер получает объектные события только при подтверждённой связи в нужной дисциплине; эту связь повторно проверяют при чтении и перед отправкой. Перед отправкой также проверяются активность пользователя и наличие роли.

## Планировщик и повторные попытки

`docker compose exec -T api python manage.py process_notifications` выполняет один цикл; сервис `notifications` запускает `--loop`, цикл каждые 30 секунд. Повторный запуск безопасен: уникальные ключи предотвращают повторную постановку. Два worker не отправляют одну строку одновременно благодаря PostgreSQL `SELECT FOR UPDATE SKIP LOCKED`.

Напоминания: открытая регистрация за 7 дней, текущие разряды/категории за 60 дней (разряды группируются по человеку и дисциплине), сроки отчётов за 30 дней, ходатайства на премии Губернатора до 1 февраля за 60 дней. Дата присутствует в названии напоминания. Автоматический расчёт премий D8 не реализуется в этом задании.

При ошибке сохраняются имя класса ошибки, число попыток и время следующей попытки, без необработанного текста SMTP. Интервалы 60, 120, 240, 480 секунд; после пятой неудачи — `failed`. Транспорт имеет timeout 10 секунд. Удалённая роль или утраченная связь приводит к `cancelled`. Сохранённая история не удаляется.

SMTP не предоставляет транзакцию с PostgreSQL: при принятом сервером письме и аварии до фиксации `sent` возможна повторная доставка. Это **at-least-once**, гарантии exactly-once не заявляются. `sent` означает принятие письма SMTP, а не прочтение или гарантированное попадание в папку «Входящие».

## Локальная проверка и production

`docker compose up -d --build` запускает Mailpit и worker вместе с API. Mailpit доступен только на loopback: `http://localhost:8025`; SMTP порт не публикуется на хост. На отдельном стенде задайте `FSP_MAILPIT_PORT` и точный `DJANGO_CSRF_TRUSTED_ORIGINS` с выбранным портом frontend. Проверка `mandatory-live.spec.ts` использует `FSP_MAILPIT_URL` (по умолчанию `http://127.0.0.1:18025`). Для стандартного Compose укажите `http://127.0.0.1:8025`.

Настройки реального провайдера задаются вне Git: `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS` или `EMAIL_USE_SSL`, `DEFAULT_FROM_EMAIL`. Одинаковые значения передаются API и worker. После настройки выполните контролируемое событие, проверьте запись `sent` и получение письма в целевом ящике. Без credentials и подтверждения получения реальная внешняя доставка остаётся **unverified**. Mailpit доказывает локальную SMTP интеграцию, но не доставку production провайдером.

Тесты: `test_notifications.py`, `test_notifications_concurrency.py`; браузерная проверка `mandatory-live.spec.ts`. Фактические результаты конкретного прогона фиксируются в итоговом отчёте и матрице приёмки.
