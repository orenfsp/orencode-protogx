# Приёмка ветки руководителем

Получите handoff из [TASK_ASSIGNMENT.md](TASK_ASSIGNMENT.md): Task ID, автор, branch, base/final commit, изменённые файлы, API/DB изменения, фактические команды/результаты, ограничения, зависимости, конфликты. Без remote допускается локальная ветка/hash; не называйте её PR.

1. `git status --short --branch`: проверьте чистоту интеграционной ветки и base commit. `git diff --name-status main...<branch>` — каждый путь входит в allowlist; нет `.env`, секретов, зависимостей, реальных PII, случайных PNG.
2. Убедитесь, что задача ровно одна, Phase 3 не начата без разрешения, shared контракт не изменён обходным путём. Просмотрите не только diff, но и вызывающие места.
3. Сверьте backend модели/миграции/сериализаторы/views/services с [API_CONTRACTS.md](API_CONTRACTS.md), `docs/openapi.yaml`, frontend DTO и `AGENTS.md`. Любую новую модель, роль, auth/CSRF, endpoint или дизайн токен принимают только после явного решения руководителя.
4. Проверьте отрицательные границы: анонимный доступ, неправильная активная роль, чужой объект, minor/guardian, связь coach, приватный snapshot и download. Новое бизнес-правило исполняется на сервере; audit и транзакция покрывают изменение.
5. Выполните релевантные команды из [TESTING.md](TESTING.md) в интеграционном окружении. Сохраните точные числа тестов и exit codes, отдельно укажите непрогнанное.
6. Для UI сравните с [reference HTML](../design/fsp-reference.html) на desktop/tablet/mobile в обеих темах, навигацию/таблицу/focus/ошибки/пустое состояние; `check_design_contract.py` должен пройти. Не принимайте дизайн по одному screenshot.
7. Проверьте `git diff --check`, внутренние ссылки документации, миграционный drift и совместимость с соседними ветками. Конфликты общих файлов разрешает владелец контракта, затем повторяются затронутые тесты.
8. После review объедините через PR, если есть хостинг, либо контролируемый локальный merge; не force-push/reset shared ветку. Зафиксируйте merge hash и обновите [матрицу приёмки](../acceptance-matrix.md) только на основании исполненного evidence.

Если пункт не проверен, зафиксируйте его как открытый gate, а не как pass. DeepSeek/MCP отзыв — предложение: руководитель проверяет релевантность, paths и факты до применения.
