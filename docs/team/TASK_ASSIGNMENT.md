# Выдача задач и handoff

1. Руководитель сверяет `git status`, базовый commit и [CURRENT_STATUS.md](CURRENT_STATUS.md); формулирует одну измеримую задачу. Разбивает пересекающиеся изменения на зависимые этапы и закрепляет одного владельца за каждым файлом.
2. Заполняет [TASK_TEMPLATE.md](TASK_TEMPLATE.md): branch, точный allowlist/denylist, существующие интерфейсы, AC, тесты. Для внешнего AI участник добавляет [bootstrap prompt](AGENT_BOOTSTRAP_PROMPT.md). Не давайте агенту неограниченное «сделай Phase 3».
3. Участник работает в task-ветке. Если требуются изменения вне allowlist, останавливает зависимую часть и сообщает proposal руководителю с последствиями для DTO/прав/БД. До ответа можно выполнять независимые тесты и документацию внутри назначения.
4. Участник отдаёт PR или hash ветки и структурированный отчёт ниже. Руководитель применяет [INTEGRATION_CHECKLIST.md](INTEGRATION_CHECKLIST.md), затем объединяет через поддерживаемый хостинг либо согласованный локальный merge.

## Отчёт после каждой задачи

```text
Task ID:
Contributor / AI assistant (если использован):
Branch / base commit / final commit:
Что изменено:
Файлы:
API/DTO/модели/миграции/права: нет | предложение | утверждённое изменение
Команды проверок и фактические результаты (код выхода, число тестов):
Визуальная проверка (если UI):
Ограничения и неготовые части:
Зависимости интеграции:
Неразрешённые конфликты:
```

Отчёт без реально выполненных команд не называется «всё прошло». Handoff не даёт автору права merge в `main`. Порядок рассмотрения: проверка scope → shared контракты → права/данные → тесты → дизайн → merge safety. Если нет remote, руководитель сначала предоставляет URL/права доступа; локальную ветку нельзя выдавать за открытый PR.
