# Пять участников и владельцы файлов

Разделение опирается на раздел 15 [Master Prompt](../MASTER_PROMPT.md), но пути ниже отражают **текущий** репозиторий. Участники 2–5 работают в отдельных ветках и могут использовать любой AI; доступ к локальному DeepSeek MCP, секретам, окружению или сессии руководителя **не предполагается**. Само существование роли не запускает Phase 3.

| № / область | Текущие разрешаемые по заданию файлы | Результат и обзор |
| --- | --- | --- |
| 1. Руководитель, Codex + доступный DeepSeek MCP | `backend/config`, `accounts`, `catalogs`, общие миграции, `docs/openapi.yaml`, `frontend/src/lib/api.ts`, `AppShell.tsx`, `globals.css`, `app.css`, Compose, общие docs | фиксирует DTO/права/токены, раздаёт задачи, проверяет и объединяет ветки; MCP — только ограниченное внешнее предложение |
| 2. Соревнования backend | по конкретному заданию `backend/apps/competitions/{services,serializers,views,exporters}.py`, `backend/tests/test_competitions.py` | тестируемые доменные изменения/исправления; любое изменение модели, route или DTO сначала согласовать |
| 3. Спортивная область backend | пока **только изолированные тесты, исследование и предложения** в выделенных новых документах/тестах; будущие `registry`, `qualifications`, `ratings`, `analytics` ещё не существуют | готовит контракт будущей задачи; без отдельного старта Phase 3 не создаёт модуль/миграцию |
| 4. Интерфейс федерации | по заданию `frontend/src/app/competitions/`, `frontend/src/components/CompetitionEditor.tsx`, `TemplateEditor.tsx` и отдельный тест | работающие экраны управления, визуальная проверка; не меняет общий shell/CSS/DTO |
| 5. Интерфейсы athlete/coach/judge и QA | по заданию `frontend/src/app/{history,coach-links,dashboard}/`, `frontend/tests/`, `frontend/scripts/` | ролевые потоки, Playwright, визуальная проверка и handoff; не меняет общие интерфейсы |

Это **матрица ответственности**, а не постоянное разрешение редактировать все указанные файлы: точный allowlist даёт [контракт задачи](TASK_TEMPLATE.md). В частности, `[id]/page.tsx` содержит UI нескольких ролей и назначается одному автору в момент работы; два участника не правят его одновременно. `frontend/src/components/ResultEditor.tsx` пересекает federation/judge UI и тоже получает одного владельца. `backend/apps/competitions/models.py`, миграции, `urls.py` — shared контракты, только после решения руководителя. Не создавайте параллельно новые app с пересекающимися моделями.

## Зависимости и приёмка

Последовательность для будущей доменной задачи: руководитель фиксирует model/DTO/permission → backend владелец реализует и тестирует → UI владелец интегрирует по утверждённой схеме → QA проверяет роль, объект, mobile/theme и end-to-end → руководитель проверяет контракт и merge. Если backend и UI разрабатываются параллельно, mock должен быть локальным и удалён до приёмки; статическая демонстрация не считается завершённым workflow.

В текущем документационном спринте можно раздать независимые задачи на тесты, обнаружение пробелов или уточнение документации. [TASK_ASSIGNMENT.md](TASK_ASSIGNMENT.md) содержит порядок выдачи. Review: автор проверяет собственный diff/тесты, другой участник смотрит назначенную область, руководитель принимает любые shared и интеграционные решения.
