# Правила для любого внешнего AI coding agent

Эти правила независимы от Codex, Claude, Cursor, DeepSeek, Qwen или другой платформы. Руководитель — единственный интегратор shared архитектуры. AI получает только [контракт задачи](TASK_TEMPLATE.md) и локальный репозиторий участника; доступ к локальному MCP руководителя не требуется и не предполагается.

1. До реализации прочти `AGENTS.md`, `docs/MASTER_PROMPT.md`, `docs/acceptance-matrix.md`, `docs/team/README.md` и документы, указанные в задаче; для UI обязательно прочти `docs/design/fsp-reference.html` и `frontend/AGENTS.md`.
2. Проверь фактический код, текущий `git status`, ветку и base commit. Не предполагай методы, endpoints, модели или готовность будущих модулей по плану.
3. Выполняй только явно назначенную задачу и работай только в указанной ветке и allowlist путей. Если branch/ownership/контракт неоднозначен, уточни до кросс-модульной правки.
4. Сохраняй существующую архитектуру, поведение, ограничения доступа и текущие данные. Не делай спекулятивный rewrite, массовый refactor или «улучшения заодно».
5. Не меняй самостоятельно `accounts.User`, `UserRole`, guardian/consent, общие модели и миграции, authentication/session/CSRF, permissions, маршруты и DTO/OpenAPI, `AppShell`, глобальные CSS токены или Compose. Для необходимых изменений сначала отправь proposal руководителю и дождись утверждённого контракта.
6. Следуй неизменяемому reference HTML: нумерованная индиго-панель, dotted navigation, document rail, оранжевые акценты, шрифты, штампы, границы, темы, mobile bottom nav. Не редактируй reference и не выполняй самостоятельный redesign.
7. Используй имеющиеся компоненты, `api<T>()`, сервисы и тестовую инфраструктуру. UI не является авторизацией: сервер должен проверять роль и объект.
8. Добавляй/обновляй релевантные тесты для поведенческой правки; запускай назначенные проверки. Не выдумывай pass, число тестов, screenshot review или факт запуска.
9. Не раскрывай API keys, `.env`, cookies, credentials, частные персональные данные. Seed и примеры — только фиктивные. Не отправляй произвольный код/секреты во внешнюю модель.
10. Не фабрикуй официальные нормы, форму протокола или соответствие ЕВСК. Демо-шаблоны требуют сверки с первоисточником; не называй их нормативно подтверждёнными.
11. Не удаляй/сбрасывай БД и тома, не применяй разрушительные миграции, не переписывай историю общей ветки и не force-push без явного разрешения.
12. Если задача требует другой модуль, файл или shared контракт, передай проблему, точный путь, предполагаемый diff и зависимость руководителю **до** реализации этой части.
13. После задачи выдай структурированный отчёт из [TASK_ASSIGNMENT.md](TASK_ASSIGNMENT.md): branch/hash, изменённые файлы, API/DB последствия, команды и фактические результаты, ограничения, конфликты.
14. Решение об интеграции, разрешении конфликтов и merge принимает руководитель.

Правило спринта: **не начинать Phase 3** без нового явного задания. Нельзя представить статический экран или mock как реализованный end-to-end workflow.
